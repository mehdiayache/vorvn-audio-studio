# Voice Studio — full product, UX and architecture audit

**Date:** 2026-08-06  
**Scope:** complete read-only review of the local application, live UI, product model, Alibaba integration, data/accounting, modularity and future API/SaaS readiness.  
**Constraint respected:** no Alibaba audio generation and no paid provider call.

## Executive verdict

The product idea is now coherent, but the implementation is not yet reliable enough for a team server or a public API.

The application should be understood as a **work-production system powered by independent tools**:

```text
Independent tools
  Composer · Batch · Voices · Subtitles · Import

                  optional destination
                           ↓

Venture (brand, policy, library, billing)
└── Project (series or campaign)
    └── Production (currently called Folder)
        └── ordered parts + reusable assets + background music
            └── immutable export
```

This distinction is essential:

- a Venture is a real brand/business scope, not a large folder;
- a Project groups related productions;
- a Production is one finished work, currently mislabeled Folder;
- tools remain globally accessible and can receive an optional destination;
- no Venture, Project or Production owns a duplicate Composer;
- Music is a static reusable library, never a sound generator;
- background finishing must remain intentionally smaller than a DAW.

The foundation is worth keeping. A blind rewrite would discard useful work. The correct next phase is a controlled correction of domain rules, finishing/export, resource types and frontend/backend boundaries, followed by a simpler work-centric UI.

## What should be preserved

- One movable Composer shared by standalone and contextual workflows.
- One reusable audio-player contract.
- Central hierarchy/workspace state instead of separate navigation implementations.
- Venture-owned reusable collections.
- Non-destructive music linking, fades and ducking.
- Alibaba provider separation under `services/alibaba`.
- Actual token usage capture for Omni streams.
- Local-only binding and owner-only secret files during the current personal-development phase.
- The v1 API intention to use durable Jobs for long or paid operations.

## Proven P0 defects

These are code-path defects, not visual opinions.

### 1. Adding silence from a Production is broken

The Projects client sends `{id, seconds}` while the server expects `project_id`. The main add-silence action and seam action share that adapter.

### 2. External subtitle upload crashes

The uploaded-file path defines the URL/playable media but later estimates from an undefined `target`, producing an `UnboundLocalError` before transcription.

### 3. Batch-result playback is broken

A DOM variable named `play` shadows the shared playback function, then the click callback attempts to call the element as a function.

### 4. Final stitch is not format-safe

The server reads every part as bytes, joins the bytes and saves the result as MP3. The application accepts or generates MP3, WAV, Opus, M4A, AAC, OGG and FLAC. Raw concatenation can create:

- WAV/OGG data inside a file named MP3;
- repeated MP3 headers and metadata;
- incompatible sample rates or channel layouts;
- wrong durations and subtitle offsets;
- exports that play in one decoder and fail in another.

Do not add more editing UI over this implementation.

### 5. Paid Speak validates the destination too late

The endpoint can synthesize and write a paid file before proving that the requested destination is a valid Production. It can receive a Venture, Project, library or nonexistent ID.

### 6. Asset and music ownership are not enforced

The server verifies that a generation has a filename, but not that it is an Asset, belongs to the correct collection or is owned by the same Venture. A future API client can bypass the UI.

### 7. Uploaded icons can receive an audio MIME type

Image files are served through a media helper that recognizes audio formats. PNG/JPG/SVG/WEBP can therefore be returned as `audio/mpeg`, which can explain unreliable venture logos.

## Correct target domain model

### Containers

- **Venture:** organization/brand identity, defaults, reusable library, billing scope and later team membership.
- **Project:** series, campaign, book or production group.
- **Production:** one concrete deliverable such as a sleeping guide, prayer, episode or advertisement.

The database can temporarily keep the legacy `folder` name, but the product and public API should move toward `production`.

### Content resources

- **Part:** ordered source segment in a Production.
- **Take:** alternate generated or uploaded realization of a Part.
- **Asset:** reusable Venture-owned content such as music, intro, outro or stinger.
- **AssetVersion:** immutable stored version plus duration and technical metadata.
- **TimelineItem:** placement of a Part, silence or AssetVersion in a Production.
- **Export:** one immutable rendered output.
- **ExportManifest:** exact ordered inputs, mix choices, format and renderer version.

### Why the current model leaks

- uploaded Assets are stored as ordinary `generations.kind='audio'`;
- the Assets root is stored as an ordinary Project;
- public Project listings can return Assets as a production Project;
- the browser identifies a library partly by the literal name `Assets`;
- library uploads inflate Venture part counts;
- stitched exports are ordinary generations without a reproducible manifest.

Immediate bridge: add an explicit `container_type` or `system_role`, exclude libraries from production lists/metrics and stop using display names as identity.

## Tool and navigation model

The top-level product should become work-centric while preserving independent tools.

```text
Work
  Ventures → Projects → Productions

Create
  Composer · Batch · Import

Library
  Voices · Venture assets

Secondary
  Activity · Settings
```

Every creation tool should expose one persistent context control:

```text
Save to: Unsorted ▾
```

or:

```text
Save to: Heartsnotes / Sleeping Guides / Christian Prayer ▾
```

Behavior:

- opened globally: defaults to Unsorted;
- opened from a Venture/Project: destination picker is pre-scoped but remains changeable;
- opened from a Production: that Production is preselected;
- changing voice/model affects the current request, not the whole folder forever;
- destination and resolved routing remain visible before the paid action.

Do not keep seven equally weighted top-level tabs. Batch and Subtitles are tools; Settings and Activity are secondary surfaces.

## Live UX audit

### Desktop Production view

Strengths:

- hierarchy, ordered sequence, finish panel and linked music are understandable;
- parts and reusable assets can coexist;
- the finish panel has a reasonable desktop role;
- Arabic text uses automatic direction in important content surfaces.

Problems:

- the workspace tree, central sequence and finish panel compete for width;
- long part names/text truncate heavily;
- actions are distributed across rows, panels and menus without one dominant task path;
- the word Folder understates what the surface actually does;
- timeline/mix state and export state are visually too close despite being different concepts.

### Tablet

At roughly 1024 px, the header wraps, the workspace rail consumes too much width and the finish panel compresses the main production sequence. The left rail should collapse before the content becomes narrow.

### Mobile

At roughly 390 px, the full expanded workspace tree appears before the production content. The user must travel through the hierarchy to reach the actual work. This is a structural responsive failure, not a spacing bug.

Required behavior:

- Workspace becomes a drawer/switcher;
- destination/breadcrumb becomes one compact control;
- only the active work surface occupies the page;
- Finish becomes a bottom sheet or separate step;
- the primary action remains reachable without scrolling through navigation.

### Composer

The current text surface is visually cleaner and Arabic direction is supported, but the information hierarchy is still wrong:

- destination/context is not dominant enough;
- model/provider is more visible than user intent;
- a blank or em-dash voice selector is not understandable;
- Settings is duplicated between quick controls and a larger settings surface;
- large empty areas do not improve focus because the required decision path remains unclear.

Recommended order:

1. destination;
2. text;
3. voice;
4. mode: Exact reading or Directed performance;
5. language/routing confirmation;
6. Generate;
7. Advanced: raw model, format, seed, provider-specific controls.

### Venture and Project views

The views are now more distinct than before, but still inherit too much generic card UI.

- Venture should look like a brand home: logo, identity, active productions, library and business-level status.
- Project should look like a production collection: progress, productions, latest work and create-production action.
- Production cards should prioritize title, state, duration/progress and last activity.
- long names require responsive list/card variants, not narrower repeated cards.
- the Workspace tree duplicates card navigation and becomes noise on overview pages.
- generic icons must not substitute for Venture identity when a real logo exists.

### Settings

The current page exposes about ten technical cards at once and mixes different ownership scopes.

Split it into:

- **Personal/machine:** theme, local output directory, reference storage, disk;
- **Studio admin:** API/provider credentials, advanced interpretation, pronunciation dictionaries, spend policy;
- **Venture:** brand identity, naming/defaults, approved voices, libraries;
- **Project/Production:** only contextual settings that truly belong there.

Use progressive disclosure. Prompt internals and provider-specific flags should not be adjacent to ordinary naming controls.

### Accessibility

- hierarchy card buttons contain nested settings buttons; keyboard events can bubble and open both;
- waveform seeking is pointer-only and lacks slider semantics;
- shared drag/drop lacks one shared rejection, busy, retry and partial-failure pattern;
- some backend errors are inserted through `innerHTML` without consistent escaping;
- responsive and keyboard journeys are not covered by automated browser tests.

## Minimal audio finishing — not a DAW

The requested sleeping-guide workflow needs a bounded non-destructive finishing layer:

### Primary lane

- reorder spoken parts, silences, intros, outros and stingers;
- trim start/end of a clip;
- gap before/after;
- per-item gain;
- short fade in/out.

### One background lane

- choose an Asset from the Venture Music library or upload by click/drag-and-drop;
- trim music start/end;
- start offset, including “start before voice”;
- end behavior: Repeat to fill, Play once, or End with production;
- background gain;
- fade in/out;
- duck under speech;
- optional tail after final speech.

### Deliberate exclusions

- no arbitrary multitrack canvas;
- no automation curves;
- no plugins/effects rack;
- no destructive waveform edits;
- no music generation inside the static Music library;
- no free-positioning every spoken clip in v1.

All controls store timing/mix metadata. Original audio remains untouched. Rendering occurs only at Finish.

## Export architecture

Replace stitch with one manifest-driven FFmpeg finishing service:

1. resolve and authorize all source versions;
2. decode every input;
3. normalize sample rate, channel layout and timebase;
4. apply trim/gain/fades;
5. insert deterministic gaps/silence;
6. concatenate the primary lane;
7. position/loop/fill/duck/mix the background lane;
8. encode once to the requested target format;
9. validate duration and decodability;
10. persist checksum, manifest and renderer version.

An ExportManifest must retain:

- exact take/asset version IDs;
- ordered timeline items;
- trim, gap, gain and fade values;
- music version and mix settings;
- subtitle versions;
- codec, bitrate/sample rate and channels;
- renderer version;
- final duration and checksum.

## Alibaba/Qwen audit

### Current strengths

- Qwen Audio and Qwen 3.5 Omni are no longer treated as interchangeable APIs.
- cloned Omni voices remain bound to compatible Omni models.
- Qwen Audio is used for exact TTS and Omni for instruction-driven performance.
- Omni stream usage can be captured from returned usage rather than only estimating characters.
- the machine-translation route follows the OpenAI-compatible Qwen-MT contract.

### Current official position

As of this audit, Alibaba recommends Qwen Audio 3.0 Plus for high-quality standard TTS and Qwen Audio 3.0 Flash for voice cloning. The app is therefore using a current exact-TTS family rather than an obsolete one.

Qwen 3.5 Omni remains valuable for naturally directed audio output, but exact reading and directed performance are different product outcomes. They should be explicit modes rather than accidental consequences of a model dropdown.

CosyVoice 3.5 adds Voice Design and instruction-oriented controls. Voice Design is a useful missing capability later: create a reusable voice from a text description without a reference recording. It should enter through the same voice/provider registry, not as another top navigation tab.

Qwen-MT supports more than basic language selection: terminology, domain hints and translation memory. The current app uses the correct family but underuses these production controls. They belong in Venture/Project dictionaries and advanced translation, not in the everyday Composer path.

For long-file transcription, the current Qwen ASR route is reasonable. Context enhancement, proper-noun vocabulary and speaker diarization are more valuable future additions than live translation for the current sleeping-guide workflow.

### Required provider/model registry

Model names should not be product navigation. Create a registry describing:

- provider and product family;
- region/workspace and endpoint;
- supported languages;
- voice type and remote voice identity;
- required bound model;
- exact-reading reliability;
- instruction/emotion support;
- cloning/design support;
- formats and limits;
- billing unit and price-table version;
- health/capability probe results.

The user chooses an outcome such as Exact reading, Directed performance, Faster draft or Publishing quality. The router resolves the implementation.

Before generation, return and display:

```text
requested language / voice / outcome
resolved provider / model / voice / endpoint
warnings or incompatibilities
cost estimate when available
```

Never silently replace a selected voice with Tina or another fallback. Reject the combination or require explicit approval.

### Region and endpoint

Workspace-specific Singapore endpoints are currently recommended by Alibaba. The app contains an Omni endpoint workaround based on an observed streaming-audio issue. Do not delete it blindly. Replace it with:

- configured primary endpoint;
- startup/periodic capability probe;
- controlled documented fallback;
- per-Job recording of the endpoint/region actually used.

### Voice metadata

Persist provider identity instead of relying on name prefixes:

```text
provider
remote_voice_id
region/workspace
voice_type
bound_model
languages
status
creation_source
created_by
Venture ownership or global visibility
```

### Clone UX rules

The clone UI should clearly validate and explain Alibaba’s current sample guidance: approximately 10–20 seconds recommended, at least 5 seconds of continuous speech, maximum 60 seconds/10 MB, at least 16 kHz and no music/noise. Language choice and the model family receiving the cloned voice must remain visible.

## Activity, usage and money

The Activity UI is a useful base and correctly distinguishes actual values from estimates in places. It is not yet an exact financial ledger.

Known gaps:

- multilingual speech can pay for translation but log only speech;
- some batch failures escape before being logged;
- voice description/transcription failures can remain “running” until a stale sweep;
- failed or partial provider work is often recorded as zero cost;
- rewrite, translation, ASR and description use fixed estimates in some paths;
- provider request ID, region/endpoint and price-table version are not consistently retained;
- concurrent same-text jobs can collide because several filenames use second-level timestamps;
- library uploads inflate production metrics because Assets are generations.

For every Job, record:

- operation and user/tenant;
- idempotency key;
- requested and resolved routing;
- provider request ID;
- region/endpoint;
- input/output usage by billing unit;
- actual/estimated/unknown cost status;
- price-table version and currency;
- timestamps, retries and final status;
- produced resources/files;
- error envelope without secrets.

Never imply precision where Alibaba did not return exact usage. Show Actual, Estimated or Unknown explicitly.

## API and job architecture

The existing v1 read API is a useful contract sketch, not a public production API.

Paid writes must not execute synchronously inside an HTTP request. A timeout followed by retry can duplicate charges.

Minimal durable model:

1. authenticate and authorize the destination;
2. require an `Idempotency-Key`;
3. validate all domain invariants;
4. create a queued Job transactionally;
5. return `202` with the Job resource;
6. execute with a Postgres-backed worker;
7. persist provider request, usage, retries and outputs;
8. support polling and later cancellation.

Postgres is sufficient initially. Kafka, Redis and microservices are unnecessary.

## Backend boundaries

The current `server.py` and `db.py` mix HTTP, validation, domain rules, providers, persistence and file handling. Introduce boundaries incrementally:

```text
backend/
  domain/
    hierarchy.py
    assets.py
    productions.py
    jobs.py
    exports.py
    routing.py
  application/
    commands.py
    queries.py
  providers/
    alibaba/
  infrastructure/
    postgres.py
    files.py
    ffmpeg.py
  http/
    legacy.py
    v1.py
```

All callers must use the same domain commands:

```text
CreateTake(destination)
LinkAsset(asset, production)
SetBackground(asset, production)
MoveTimelineItem(item, production)
CreateExport(production)
```

The UI cannot be the security or integrity boundary.

## Frontend boundaries

The extractions are real but incomplete. `app.js` remains roughly 5,700 lines and still owns direct networking and orchestration for multiple non-Project features.

Target:

```text
ui/
  core/
    router
    events
    api-client
    session
  components/
    player
    destination-picker
    file-drop
    status
    dialogs
  features/
    work/
    composer/
    voices/
    assets/
    batch/
```

`app.js` should become boot, route composition and cross-feature event wiring only.

Do not migrate to React/Vue solely because one file is large. Stabilize the domain/API contracts and component behavior first. A future UI replacement then becomes substantially safer.

## Data, storage and security gates

The current localhost binding is the only meaningful perimeter. That is acceptable for user number one on one machine, but the app must not be put behind a public reverse proxy today.

Before team/server/SaaS exposure:

- authentication and organization membership;
- tenant/ownership fields and authorization on every resource;
- signed or authorized asset delivery;
- secrets manager instead of a shared editable environment file;
- object storage for durable media;
- upload MIME, size and decode validation before full in-memory reads;
- SVG sanitization or rejection;
- rate limits and quotas;
- durable idempotent Jobs;
- immutable audit records;
- versioned database migrations, constraints, backups and restore drills;
- production CSP/security headers.

## Minimal-for-maximal roadmap

### Phase 0 — make the current local product truthful

1. Fix silence, external subtitle upload and Batch playback.
2. Fix image/media MIME handling.
3. Validate destination level and same-Venture ownership before paid work.
4. Replace raw stitch with a fixture-tested FFmpeg export pipeline.
5. Add HTTP/browser regression tests for these flows.

Exit: one local fixture journey is reliable without Alibaba calls.

### Phase 1 — correct the product model

1. Add explicit container/system roles; stop detecting Assets by name.
2. Exclude libraries from project lists and production metrics.
3. Introduce Asset/AssetVersion and Export/ExportManifest.
4. Begin product-language migration from Folder to Production.
5. Make destination/context persistent in every tool.

Exit: Ventures, Projects, Productions and Assets are behaviorally distinct.

### Phase 2 — useful finishing and simpler UX

1. Add non-destructive trim, gap, gain and short fades.
2. Add one background lane with offset, fill/loop/stop, fades, ducking and tail.
3. Reorganize navigation into Work/Create/Library/Secondary.
4. Turn Workspace into a responsive switcher/drawer.
5. Split settings by scope and move provider/model details under Advanced.

Exit: a sleeping guide can be produced and finished without a separate audio editor.

### Phase 3 — modularize around contracts

1. Centralize backend commands and invariants.
2. Extract remaining frontend networking/features from `app.js`.
3. Add provider/model/voice registry and route-resolution preview.
4. Version migrations and add database constraints.
5. Complete exact/estimated/unknown usage accounting.

Exit: a second UI or internal API client can use the same safe application layer.

### Phase 4 — team/API readiness

1. Authentication, organizations, roles and authorization.
2. Durable idempotent Jobs and worker.
3. Object storage, signed delivery and unique immutable keys.
4. v1 write contracts, quotas and audit records.
5. Operational monitoring, backups and recovery.

Exit: safe internal team deployment. Public SaaS hardening follows real usage.

## Explicit non-goals now

- no full DAW;
- no framework rewrite for its own sake;
- no microservices;
- no model zoo in the main UI;
- no music generation inside the static Music library;
- no public paid API before auth, authorization, Jobs and idempotency;
- no claim of exact accounting when costs are estimated;
- no permanent voice configuration attached to a folder/production.

## Final product principle

The application should feel simple because the system resolves complexity, not because complexity is hidden unpredictably.

The user chooses:

- what they are making;
- where it belongs;
- which voice/outcome they want;
- a small set of finishing choices.

The system owns:

- provider/model compatibility;
- destination and ownership invariants;
- durable paid Jobs;
- exact or honestly labeled usage accounting;
- reproducible export manifests;
- safe media normalization and rendering.

That boundary is the shortest path from the current local prototype to a trustworthy team product and, later, a SaaS.
